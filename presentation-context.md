# Presentation Context: Autoresearch на практике

## Конференция и аудитория

- **Конференция:** ODS.ai
- **Секция:** Code Generation (AI4SE)
- **Слот:** 20-25 минут + 5-10 минут вопросы
- **Аудитория:** Преимущественно ML-инженеры, многие используют AI-агентов, но относительно наивно
- **Стратегия подачи:** Не объяснять ML-концепции — аудитория их знает. Показать зеркало: "вы уже знаете как это решать, просто не применяли к этой задаче"

---

## Главная мысль

> **"Без правильной метрики и данных результат агента случаен — но ML-инженер уже знает, как это чинить."**

**Что аудитория уносит с собой:** Autoresearch — это ML-pipeline для кода. Метрика + цикл итераций = агент сам находит решение.

## Блок 1: Крючок (слайды 1-2)

**История:** Пришёл на проект — сервис написан быстро, но с долгом. Надо инвестировать в рефакторинг. Решил дать работу агенту: "вот проект, найди все проблемы, реши их, сделай PRы".

**Результат:** Агент нашёл десятки поверхностных замечаний — механические правки, большие файлы, именование. Пропустил слона: размытая ответственность классов, протекающие абстракции.

**Почему так:** У агента не было метрики глубины. Он оптимизировал то, что легко измеримо, и проигнорировал то, что требует суждения.

**Функция крючка:** Показать проблему до того, как объявлена тема. Аудитория узнаёт себя.

## Блок 2: Эволюция мышления (слайды 3-4)

Лесенка от наивного к autoresearch:

1. Спрашиваем ChatGPT → копируем ответ
2. Копируем код в чат, просим что-то сделать
3. Заставляем агента работать, скармливаем контекст
4. Говорим что сделать, настраиваем .md файлы, rules (~середина 2025)
5. **Конец 2025 — перелом:** модели перешли какую-то черту. Правильная задача + правильный контекст = правильное решение

**Три события-триггера для autoresearch:**
- Модели качественно изменились в конце 2025
- Хакатон по созданию агентов общего назначения: победил не агент с детерминированным кодом и не написанный через фреймворки — победил тот, который умел на ходу улучшать себя
- Андрей Карпатый выпустил статью про autoresearch

## Блок 3: Параллель с ML (слайд 5)

**Аналогия:**
- Старый подход к оптимизации кода = ML-инженер, который руками трогает отдельные части модели и смотрит как поменялось поведение, вместо автообучения
- Autoresearch = запустить обучение: метрика + цикл + автокоррекция

**Ключевой инсайт для аудитории:** То, что кажется нормальной разработкой, с точки зрения ML выглядит как ручной перебор гиперпараметров.

---

## Блок 4: Определение Autoresearch (слайд 6)

**Минимальный flow:**
1. Выбрать одну (желательно) или несколько метрик
2. Запустить цикл: агент → автоисправление → проверка метрики
3. Стабилизирующие метрики: тесты, типизация, линтер

**Откуда термин:** Андрей Карпатый, autoresearch / self-improving systems

## Блок 5: Кейс 1 — Оптимизация производительности .NET (слайд 7)

**Почему сложно классически:**
- JIT-компиляция в несколько этапов
- Сборщик мусора
- Оптимизации рантайма (проверка границ массивов, инлайнинг)
- Всё это меняется с каждой версией — знания устаревают
- Вывод: любые оптимизации нужно подтверждать бенчмарками

**Старый способ:** Написать бенчмарк → изменить код / заменить библиотеку → запустить бенчмарк → посмотреть → повторить вручную

**С autoresearch:** ~10 итераций → ~10x ускорение на конкретных функциях

## Блок 5: Кейс 4 — Автоматический рефакторинг (слайд 10)

**Возврат к крючку:** "Помните, в начале я рассказывал про рефакторинг?"

**Что изменилось с autoresearch:**
- Взяли метрики: цикломатическая сложность, глубина вложенности, направление зависимостей (domain → application и т.д.)
- Важно: выбирали только бесспорные метрики — не холиварные
- Скормили агенту с циклом автоисправления

**Результат:** Значительно больше замечаний пофикшено, значительно быстрее. Каждый коммит обоснован ("цикломатическая сложность была 14, стала 4")

**Ограничение — это важно:** Архитектурные решения пока не ложатся в метрики — "когда применить State Machine", "когда Abstract Factory действительно помогает". Опытный инженер чувствует это, метрики — нет.

## Блок 6: Что работает / что нет (слайд 11)

**Работает хорошо:**
- Чёткие измеримые метрики (время, сложность, покрытие)
- Механические правки с ясным направлением
- Итерации где каждый шаг верифицируем

**Работает плохо:**
- Архитектурные решения без метрик
- Задачи где "правильность" субъективна
- Слабо определённая цель ("сделай лучше")

## Блок 7: Финал (слайды 12-13)

**Вывод 1 (нейтральный):** Опытные инженеры пока не заменяются — архитектурное мышление, паттерны, проектирование не имеют метрик.
